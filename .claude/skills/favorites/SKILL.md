## Favorites Page (`/favorites`)
Its **layout** (inner-scroll column, pinned tabs, overscroll suppression, `data-scroll-container`) is documented under [Pages that own the viewport](#pages-that-own-the-viewport-inner-scroll--favorites) — check there before changing anything about its height, header or scrolling. Data behaviour follows.

Optimistic unfavorite, auto-sync on page load. **Playlist favorites gotcha**: `isPlaylist()` and `playlistImageFallbacks` must use **lowercased feedId**, not the human name. `playlistSlugOverrides` handles ID-to-slug mismatches. Nostr playlist publishing: Kind 34139 addressable event (`d` tag = `stablekraft-favorites`).

**Three `Feed` `select` blocks gotcha** (`app/api/favorites/tracks/route.ts` GET): tracks are matched by id, then guid, then audioUrl — three separate `prisma.track.findMany` queries whose results are concatenated into one `tracks` array. When adding a `Feed` field, add it to **all three** selects or `tsc` rejects the `[...tracks, ...tracksByGuid]` concat (the arrays have incompatible `Feed` shapes) and the Railway build fails at the type-check step — not caught locally unless you run `npm run build`. Same family as the albums-fast dual-select gotcha above.

## `FavoriteAlbum.feedId` is POLYMORPHIC — every read path must expand it
A row may hold a `Feed.id`, a `Feed.guid`, or a synthetic `artist-*` id, because the call sites write whichever the album object in hand carried (the home list rows send `album.feedId || album.feedGuid`). **Any path that compares the string it was handed will miss favorites the user can plainly see.**

- **The symptom is an album sitting in `/favorites` with an unfilled heart.** `GET /api/favorites/albums` resolves all three formats (id map → `guid` column fallback → synthetic artist ids), so the album renders; `/api/favorites/check` compared exactly, so its heart read unfavorited on the card and on its own album page. Reported against a **14-track** album — unrelated to the single-track rule below, which is a separate divergence in the same feature.
- **`/api/favorites/check` expands both kinds now.** The tracks branch already resolved `id`/`guid`/`audioUrl`; albums resolve `id`/`guid` the same way and count a hit on any of them. The asymmetry is what hid this — one branch grew the expansion and the other didn't.
- **`DELETE /api/favorites/albums` expands too, and must.** Exact-match there 404s on a row stored under the other format, so the heart would turn on after the check fix and then refuse to turn off.
- **The expansion lives once, in `lib/favorite-feed-ids.ts`** (tests: `npx tsx --test lib/favorite-feed-ids.test.ts`), used by `check`, and by POST/DELETE/PATCH via `expandFeedIdCandidates` in the albums route. It was written out three times with three behaviours before that — the same road `lib/feed-lookup.ts` was extracted from, and for the same reason recorded there. Do not re-inline it.
- **Collect ALL matching feeds, never the first.** `Feed.id` is the primary key and `Feed.guid` is `@unique`, so one input string can match two rows — feed A by `id`, feed B by `guid` — and `feeds.find(...)` dropped the other's identifiers. Reachable today: `app/api/playlist/resolve-mmm-tracks/route.ts` mints a feed whose **`id` IS a podcast guid** (leaving `guid` null), and a later normal import of the same show adds a second row with a slug `id` and `guid` set to that same string. **The identifiers that matter are the SECOND row's** — for input `G` the union is `{G, the-slug}`, whereas `find(...)` returning the guid-id row first yields only `{G}`. Reading just what the guid-id row contributes ("nothing new, its id IS the input") mistakes the whole thing for a no-op; the value is the row `find` didn't return. That misreading has happened twice in review, so a test pins the shape. Note this is a *widening*: when two rows collide on one string their favorites become interchangeable for that input, which is intended here (two rows sharing a guid are the same feed duplicated) but is a decision, not a side effect. Tightening it back to a single match silently restores the bug.
- **Reads union the set; writes must narrow it back to ONE row.** The widening is right for paths that OR (`check`) or `deleteMany` (`DELETE`). It is wrong for a path that mutates a single row: `findFirst` over a widened `IN` has no exact-match preference and no `orderBy`, so it picks whichever row Postgres yields — the `feeds.find(...)` arbitrary pick relocated, not fixed. `POST`/`PATCH` go through **`pickFavoriteRowForWrite`** (exact `feedId` first, then sorted for determinism). Duplicate rows are the *premise* of this expansion, and `syncFavoritesToNostr` PATCHes once per row with that row's own `feedId` — an arbitrary pick gives one row the event id published for the **other** row's `d` tag and leaves the other with none. Same reason `lib/feed-lookup.ts` keeps its rung 1 exact. A test pins that DB row order cannot change the answer.
- **Widening a delete means widening what it reports.** `DELETE` removes every row in the candidate set, so it returns **`nostrEventIds`** (plural) and `FavoriteButton` publishes a kind-5 for each. Returning one id let the other rows' kind-30001 events stay live on relays and keep surfacing in the Community tab for something the user unfavorited — the widening manufacturing orphans.
- **PATCH must not overwrite a non-null `nostrEventId` silently.** Kind 30001 is addressable, so a republish only replaces the event at the **same `d` tag** — and the widened lookup can land this PATCH on a row that published under a different one. Blind overwrite made the older event unreachable by `queueFavoriteDeletion` forever. It now keeps the newest and returns **`supersededEventId`** so the caller can kind-5 the old one; keeping the older instead would strand the newer.
- **PATCH matters more than it looks.** It lands the `nostrEventId`, and `queueFavoriteDeletion` needs that id to publish the kind-5 — so an exact-match PATCH that misses means unfavoriting can never propagate on the 30001 channel for that row, while the cross-app kind:10333 list keeps working (removal there is absence from the next revision). One channel silently degrades and the other doesn't, which is why it went unnoticed.
- **POST dedupes across the set too**, so favoriting can't mint a second row in a different format — that is where the divergence the other paths compensate for comes from.
- When adding a favorites read path, resolve the equivalence set. Do **not** "clean up" by normalizing on write alone — historical rows exist in every format and there is no migration.

## Album vs track favorites — `singleTrackFavoriteData()`, never inlined
`FavoriteButton` decides which store a favorite goes to from one expression: `const isTrack = !!(singleTrackData?.id || trackId)`. So **whether an item is filed as a track or an album was a property of the SCREEN, not the item.** The home list rows passed `feedId` alone (album favorite) while `AlbumCard` and `AlbumDetailClient` passed track data for a one-track release (track favorite) — so a single favorited from the "New" tab read as *unfavorited* on its own album page. The row was never lost; it was under the other kind. The two id chains had drifted too: `AlbumCard` carried a `track.id` rung the album page lacked, so a track with neither guid nor url resolved to a different key on each surface.

- **Every album-level heart passes `singleTrackFavoriteData(album)`** (`lib/favorite-target.ts`; tests: `npx tsx --test lib/favorite-target.test.ts`). Call sites: `AlbumCard`, `AlbumDetailClient` (**both** the desktop and mobile action rows — same duplication family as `albumBoostProps`), the four home list rows in `app/page.tsx`, and `PublisherDetailClient` (×2). Adding a surface? Use the helper — do not re-inline `tracks.length === 1 ? {...} : undefined`.
- **Absent `tracks` must NOT be read as "not a single track."** A surface that never loaded them can't tell a single from a ten-track record, and guessing is what split one album across two keys. The helper returns `undefined` for missing/null `tracks`, which means "favorite it as an album".
- **The check reads BOTH stores and remembers which one answered** (`favoriteSource` in `FavoriteButton`). Rows written before the unification still exist in both shapes, so a heart that only asked about the kind its own surface would write is the original bug. **The DELETE must target where the row actually is** — deleting the kind this surface would have written removes nothing, and the heart comes back on the next load. The optimistic add sets the source too, so an immediate unfavorite hits what was just written.
- This reaches the cross-app list: an album favorite maps to `podcast:guid:` and a track favorite to `podcast:item:guid:`, so before the fix the same release could ride the shared event as two different identifiers depending on where it was tapped.

## The favorite-status cache — a cached `false` is a KNOWN answer (`contexts/BatchedFavoritesContext.tsx`)
The other half of the two sections above, and the one that looks identical to them from the outside. **The same symptom — an album listed in `/favorites` with an unfilled heart — has a purely client-side cause that never reaches the server**, so it survived two rounds of server-side id-expansion fixes (#188, #189) that had nothing to do with it (issue #190).

`BatchedFavoritesProvider` is mounted in the **root layout**, so its `favoriteStatuses` map outlives every client-side navigation. `checkFavorites` short-circuits on any id already in that map, and `false` is in the map — so a stale entry means the heart renders unfavorited **with no request made**. Favoriting from the home grid used to update only `FavoriteButton`'s own `setIsFavorite`, leaving the `false` cached when the card first mounted; tapping through to `/favorites` then read it back. **A hard reload "fixed" it**, which is exactly what made it look like a server bug — and is the one-step diagnostic that tells the two families apart.

- **Every writer writes through.** `setFavoriteStatus(kind, id, value)` on the context, called from `toggleFavorite` on the optimistic update **and** on the failure rollback, keyed to the store the request actually mutates (`removeAsTrack`/`removeItemId` on a delete — the store the row is really in, not the one this surface would have written). A writer that updates only component state re-creates #190 exactly.
- **Bulk writers clear instead.** `FAVORITE_STATUSES_INVALIDATED_EVENT` (`lib/favorite-status-cache.ts`) — dispatched by `pullSharedFavorites` when the reconcile reports changes (the route returns counts, not ids) and by delete-all in `DangerSettings`. Both mutate rows with nothing else to invalidate them; neither reloads the page.
- **An in-flight answer must not clobber a local write.** A check can already be on the wire when the user taps. `dropClobberedKeys` + the `seq`/`localWrites` bookkeeping drop any response key written locally after the request went out. Without it the optimistic write is not durable and the heart flips back — #190's symptom in a narrower window.
- **The cache is scoped to an identity and cleared when it changes.** `favoritesIdentityKey` mirrors the API's `userId`-else-`sessionId` scoping. A check that fires before `NostrContext` hydrates goes out session-scoped and misses every `userId`-owned row — `sync-shared` writes those with **no `sessionId`** — caching `false` for favorites that exist. `FavoriteButton` gates only on `useSession().isLoading`, not `nostrLoading`, so this is reachable on the home grid (`/favorites` itself gates on both). In-flight responses from a superseded identity are discarded, not merged.
- **`isFavorite={true}` on an album card is NOT a shortcut** — `initialIsFavorite !== undefined` skips the whole check effect, so `favoriteSource` stays null and `removeAsTrack` falls back to `isTrack`. Since `/favorites` cards pass `singleTrackFavoriteData`, every **single-track** album in the Albums tab would then DELETE against `/api/favorites/tracks` for a row that is a `FavoriteAlbum` — unfavoriting silently stops working. It is only safe on the tracks tab, which passes `trackId` alone.
- Pure logic lives in `lib/favorite-status-cache.ts` so it is testable without a browser: `npx tsx --test lib/favorite-status-cache.test.ts`. The provider behaviour (root-layout survival, the rendered fill) is not — verify that with the puppeteer recipe, favoriting on the home grid and reaching `/favorites` by **clicking the link**, never `goto`, and assert `window.__noReload` survived or the probe isn't exercising the bug at all.

## Community tab (`/favorites?tab=community`, `/api/nostr/global-favorites`)
Other site users' favorites, read off Nostr and grouped **by person**. Rebuilt 2026-07-26; before that it rendered **empty for everyone since it shipped**, which read as "nobody uses this" — 8 people's favorites had been on relays the whole time, unreachable. Net effect: 26s and 0 people → **~45ms and 6 people** (8 minus two hidden test accounts).

- **Layout is people-first**: one card per person (avatar, name linking to njump, favorite count, relative time), their favorites as artwork tiles beneath, capped at 8 with a "show all" toggle so one heavy favoriter can't bury everyone below them. People are sorted by favorite count. The old per-user filter dropdown was **removed** — people are the structure now, so it was redundant; the All/Tracks/Albums filter remains and applies *within* each person, dropping anyone left with nothing. Expect a long tail of one-favorite people; that's real, don't special-case it into an "others" bucket.

- **The relay query MUST be `authors`-scoped.** Kind 30001 is generic NIP-51 ("categorized bookmarks / sets") that every Nostr client publishes, so an unscoped `{kinds:[30001,30002], limit:N}` asks for the newest N events *network-wide* and our users never make the window: measured 800 events fetched, 650 strangers, and the only site user inside them was the requester — whom `excludeSelf` then removed. Adding `authors` took it from 26s/0 people to ~4.4s/8 people. `buildFavoriteFilters()` freezes this in a test; don't drop the clause.
- **`SimplePool.querySync` takes ONE filter** (nostr-tools 2.25.2) — the three filters (typed, legacy-30002, kind-5) run as concurrent `querySync` calls and merge. Passing an array produces a malformed REQ. Uses `maxWait`, **not** an outer `Promise.race` (that discards events healthy relays already returned — same lesson as `nwc-backup.ts`). `RelayManager`/`NostrClient.getEvents` is deliberately **not** used here: it never wires `oneose`, so it always burns its full timeout.
- **Defaults must come FIRST in `buildCommunityRelays(primary, secondary)`.** Site users declare ~97 relays between them; with user relays first the 20-relay cap evicted every default, the sweep ran against arbitrary dead hosts (dead relays never EOSE → full maxWait), and the top contributor's profile came back missing because kind-0 lives on the defaults. User relays are ranked by how many users list them (`rankRelaysByPopularity`) so the cap keeps the well-shared ones.
- **Type must come from an explicit signal** — `['t','track'|'album']`, legacy `trackId`/`feedId`, or our own JSON content shape. The old kind→type fallback defaulted untyped kind-30001 to `'track'`, sweeping in `bookmark`, `pdf`, `pubcastr-*`, `Edufeed/*`, `grasp-servers`.
- **d-tag resolution is a 3-rung ladder** (`lib/nostr/favorite-item-lookup.ts`, shaped after `lib/feed-lookup.ts`): `Track.id` → `Feed.id` → `Track.guid`, bounded at 3 Prisma queries. Measured 7 / 44 / 69 with 4 unresolved — **the guid rung is 57% of all hits**; without it only 27% of the community's favorites resolved and the rest were dropped silently. Order matters: `Track.id` is sometimes a CUID and sometimes `${feedId}-${guid}`.
- **Return the CANONICAL id, never the raw `d` tag.** `originalItemId` feeds straight into `FavoriteButton` as `trackId`/`feedId`; since most d-tags are guids, echoing the tag back writes guid-shaped ids into the favorites API. The raw tag is exposed separately as `dTag` for debugging.
- **Unfavorites are honoured** via kind-5 (`collectDeletions`/`applyDeletions`) — only from the same pubkey, and coordinate (`a`-tag) deletions only kill versions at or before the deletion's `created_at` so a later re-favorite survives. Dedupe replaceable events by `(pubkey, kind, d)` *before* applying deletions.
- **This is one of two server paths that open relay sockets** (the other is `connectServerNostrClient()` in
  `lib/nostr/server-client.ts`, used by every `app/api/nostr/*` route that builds a `NostrClient`), and each has to
  bring its own WebSocket. Production runs `node:22-alpine`, whose `WebSocket` global is undici's and recurses
  with nostr-tools on a failed connect; under the Node 20 image it replaced there was no global at all. Next
  polyfills neither. So `fetchCommunityFavorites` and
  `fetchCommunityProfiles` each `await installNodeWebSocket()` **before** constructing their pool — `SimplePool`
  reads the module-level WebSocket in its constructor, so calling it after is too late. That is why `ws` is a
  production dependency and why `next.config.js` sets `serverExternalPackages: ['ws']`; webpack otherwise inlines
  `ws`, its native helpers do not survive, and every frame throws `TypeError: b.mask is not a function` as an
  `uncaughtException`. Verify against the built artifact, never the source — see Boundaries in CLAUDE.md.
- **Reached-nobody ≠ empty, and only one of them is visible.** `querySync` swallows a connect failure inside
  nostr-tools and resolves to `[]`, so the per-filter `catch` never fires and nothing is logged: the route
  answered `success: true`, `status: 'empty'`, zero people, in silence for as long as the server had no
  WebSocket. `fetchCommunityFavorites` now counts `pool.listConnectionStatus()` and returns `status: 'error'` when
  zero relays were reached. Safe for the cache — the route's `storeIfUsable` refuses to store an error, so a
  failed sweep cannot evict a good answer. Keep the two questions separate: emptiness is about events,
  reachability is about sockets.
- **Empty ≠ error.** The route returns `status: 'ok'|'empty'|'error'`; an error is never cached (server or client) and renders with a Retry. The client **does** cache empty results, but on a much shorter TTL (**15 min** vs 3h) — "nobody here yet" is the one answer worth re-checking sooner. It used to refuse to cache empties at all (`data.length > 0`), so the empty case re-ran the full sweep on every single visit.
- **Caching is stale-while-revalidate, and the freshness window is deliberately long** (`lib/caches/community-favorites-cache.ts`): fresh **3h** → serve; stale but under **24h** → serve *immediately* and refresh behind the response; older → block. A plain TTL made the ~4.4s sweep land on whichever user arrived first after expiry; SWR means only a genuinely cold instance ever waits. Other people's favorites have no urgency, so the long window is near-free: measured **40–55ms** served vs 4.4s swept, and relays get touched a few times a day per instance instead of every 90s. `refreshCommunityCache` dedupes concurrent sweeps (a burst triggers one), and a failed/`status:'error'` sweep never overwrites a good entry. `?refresh=true` forces a real sweep — that's what the UI's refresh button sends.
- The response carries `served: 'fresh'|'stale'|'fetched'` and `ageMs`, so cache behaviour is checkable from curl.
- The cache holds the payload **pre-`excludeSelf`**, so one sweep serves everyone; client sessionStorage is keyed **per-pubkey** since `excludeSelf` changes the payload, mirrors the same SWR policy, and **paints the cached list before revalidating** — a background refresh must never swap a rendered list for a spinner, nor raise an error banner over usable content (only a failure with nothing on screen surfaces one).
- The load effect must wait on `nostrLoading` — firing before `NostrContext` hydrates sends no `x-nostr-pubkey`, so `excludeSelf` silently no-ops and you see your own favorites.
- **Hiding a person from the tab**: add their **hex** pubkey to `EXCLUDED_COMMUNITY_PUBKEYS` in `lib/nostr/community-favorites.ts` (decode an npub with `nip19.decode`). They're filtered out of the author list *before* the relay query, so their events are never fetched — they stay ordinary site users everywhere else, they're just not presented to others as someone to discover. Currently holds two test accounts.
- **`lib/nostr/global-favorites.ts` is gone** (deleted in the rebuild) — its fetch path is `lib/nostr/community-favorites.ts`, its DB lookups are `lib/nostr/favorite-item-lookup.ts`. Don't resurrect it.
- Tests: `npx tsx --test lib/nostr/community-favorites.test.ts lib/nostr/favorite-item-lookup.test.ts lib/caches/community-favorites-cache.test.ts`. The relay behaviour itself isn't unit-testable — verify against prod with `curl -s localhost:3000/api/nostr/global-favorites | jq '{served, ageMs, totals}'` and check `totals.unresolved` stays low (measured 25 of ~450; a jump means the ladder is missing a rung).

## Favorite Publishers Resolution (`app/api/favorites/albums/route.ts`)
Three feedId formats: synthetic artist IDs (`artist-adam-curry`), feed GUIDs, feed IDs. Image chain: DB → PI API → album feed image by artist name.
